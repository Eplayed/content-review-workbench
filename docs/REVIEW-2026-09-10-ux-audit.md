## 一、做得对的地方（有论证，不是客套）

1. **定位与差异化成立**。市面同类分两派：卷"一键分发 20+ 平台"的全自动矩阵（踩平台红线）、纯生成流水线（无审稿无复盘）。你选"人机协同审稿闭环 + AI 腔检测"这条缝，正好落在行业公认的正确位——海外 newsroom 的 AI 落地范式就是 policy guardrails + human-in-the-loop + 闭环复盘，你三个全有。
2. **工程卫生确实好**：1641 行、1 个依赖（express）、零构建步骤、`node:sqlite` 规避原生编译、IIFE 严格模式封装、软删除、显式报错不静默降级、API Key 不进前端/不进日志、备份文件排除 Key。这是一个能长期维护的底子。
3. **服务端门禁设计正确**：清单全勾才能"已审"、无渠道不能"已发"、状态回退清空 `published_at`。这三个是真业务规则，不是装饰。
4. **信息架构清晰**：素材库→写作台→审稿台→复盘台 = 产线四步，命名即动作，新用户不用学。
5. **细节有产品感**（实测）：待办卡带逾期标红（"已搁置 5 天"）；空状态给下一步指引（"去写作台生成或粘贴一份初稿吧"）；"标记已发"明确提示"发布动作需要你人工在平台上完成，这里只做登记"——合规意识写进了交互文案。

## 二、P0 级问题：审稿闭环在 UI 上走不通（已复现 + 已修复）

### 现象
审稿台点任意文章卡片，**详情抽屉不打开**，什么都不会发生（无报错、无提示）。

### 根因
```js
// 行 497
function artById(id){ ... if(state.arts[i].id === id) return ... }   // 严格相等
```
- 卡片 HTML 里 `data-id="2"`，`getAttribute()` 拿回来的是**字符串** `"2"`
- API 返回的 `state.arts[].id` 是**数字** `2`
- `2 === "2"` 恒为 false → `artById` 返回 null → `openArt()` 提前 return（`if(!a)return;`）→ 抽屉永不打开

### 影响面（比看起来严重）
| 交互 | 状态 |
|------|------|
| 点卡片开详情（审稿唯一入口） | ❌ 断 |
| 「今天要处理」列表的"去审稿" | ❌ 断（同一函数） |
| 点卡片状态徽章做流转 `cycleState` | ❌ 断（同样走 artById） |
| 勾审稿清单 / 看检测结果 / 标记已审 / 标记已发 | ❌ 全部不可达（都在抽屉里） |
| 素材"去写作"带入 | ✅ 正常（`findMat` 行 653 已做 `String()` 双向比较） |

**这就是关键线索**：同一文件里 `findMat` 已经用 `String(a)===String(b)` 修过这个坑，`artById` 漏了——属于修了一处、漏了一处。

### 为什么没被发现
测试只覆盖服务端纯函数（detector / csv / md2html / backup，19 项），服务端门禁用 curl 验证通过；**没有浏览器 E2E**，UI 层断链没有任何测试守着。

### 修复（已做）
`artById` 改为 `String(state.arts[i].id)===String(id)`（与 findMat 口径一致）。
**实测验证**：修复后点卡片 → 抽屉打开（`drawer open`）→ 勾 4 项清单（提示变"清单全勾，可以标记已审"）→ 点「标记已审」→ toast"状态已更新：已审" → 服务端 `review_state=reviewed` 且 checklist 落库 ✅ 闭环走通。

## 三、P1 级问题（已发现，未全修）

1. **红色分级永久失效**（已修复）。前端读 `f.sev`，服务端返回 `f.severity` → 检测摘要恒显示"红 0 · 黄 6"。实测修复后为正确的"红 2 · 黄 4"。
2. **门禁失败静默无反馈**（未修，建议修）。抽屉「标记已审」在清单未勾时：服务端返回 400，但调用处 `Store.updArt(...).then(...)` **没有 catch** → Promise 拒绝被吞，用户点了没反应、不知道为什么不给过。对照：`cycleState` 那条路径有本地 guard + toast 提示。建议抽一个统一的错误提示包装。
3. **误导性隐私文案**（已修）。设置里 API Key 的 placeholder 写"仅存本机 localStorage，不上传"，而实现是存服务端 SQLite，下方说明也写对了。用户看到自相矛盾的说法会直接怀疑隐私——这是信任问题，必须零容忍。
4. **卡片不可键盘/读屏访问**（未修）。文章卡是 `div` + 事件委托，没有 `role`/`tabindex`，无障碍树里抓不到（我用 `snapshot -i` 拿不到卡片就是这个原因）。
5. **无加载/失败态**。抽屉打开依赖异步 `runDetect()`，检测慢时没有骨架屏或"检测中"提示。

## 四、针对"开箱即用 + 少配置"的差距与方案

### 核心矛盾
当前形态是**自托管 + BYOK（自带 Key）**，这两个词本身就与"开箱即用"相斥。所以要区分两件事：
- **能开箱即用的部分**：素材、手动粘稿、检测、审稿、导出、回填、周报——**全都不依赖 AI 已经可用**（这点做得对）
- **开箱不了的**：AI 生成必须配 `baseUrl + model + key` 三个字段，没有服务商预设、没有模型发现、没有本地模型自动探测

### 方案 A：把配置门槛降到"选一个 + 粘一个"（收益最大，不改架构）
1. **服务商预设下拉**：OpenAI / DeepSeek / 通义 / Kimi / Ollama（本地）/ 自定义。选预设自动带出 baseUrl 和默认 model，用户只粘 Key。
2. **模型自动发现**：`/settings/ai/test` 已经在调 `/models`，把返回的模型列表解析出来给用户选（现在是只判 ok，浪费了这次请求）。
3. **本地零配置兜底**：探测 `127.0.0.1:11434`（Ollama 默认端口），有就直接可用——**零 Key、零配置、纯本地**，这是"开箱即用"最强的卖点。
4. **设置分层**：默认只暴露"选服务商 + 粘 Key"，baseUrl/model 收进「高级」折叠。配置项从 3 个可见降到 1 个。

### 方案 B：把"不配 AI 也能用"做成显性卖点
现在 UI 没说。建议首屏或写作台直接写：**"没有 AI 也能用：粘贴你的稿子，照样走审稿→检测→导出→回填闭环。"** 顺便把「载入示例数据」从设置抽屉里提到空状态里（现在要钻设置才能找到，首次体验的白白浪费）。

### 方案 C：把你自己产线的护城河搬进来（这是最该做的一件事）
你现在有两条产线，通用版反而比自用版弱：
| 能力 | 你的生产系统（media-workbench / Dify） | 通用版现状 |
|------|----------------------------------------|-----------|
| 检测规则 | 19 条禁用句式 + 20 条安全替换 + 对比修辞密度兜底 | **3 条** |
| 一键清理 | 有（安全替换 + `.bak` 备份） | **无** |
| 发布质检门 | 有（硬门阻断复制） | **无**（检测只是提示） |
| 标题体检 | 有（公式识别 + 同质化检测） | **无** |
| 数据洞察 | 有（什么公式/时段 CTR 高） | **无**（只有周报中位数） |
三个通用化建议：
1. **检测规则扩到 20+ 条**（去掉游戏专用项，保留 AI 腔通用项），并加"一键清理安全替换"
2. **检测升格为门禁**：红标未处理不允许"标记已审"——正好复用你现有清单门禁的机制
3. **加数据洞察**：用通用维度（标题字数、是否含数字、是否疑问句、发布时段）× 回填数据算表现——**这条不依赖任何垂直领域**，是通用平台最容易做出差异化的地方

### 方案 D：分发与信任（你 9/9 已列过，补一句）
- `npx content-review-workbench` 一行试玩（比 Docker 更低门槛）
- 英文 README + 截图 + demo GIF
- 明确写"数据 100% 本地"

### 不要做的
- ❌ 多租户 SaaS、账号体系（吃掉"自托管轻量"的定位优势）
- ❌ 自动发布（你的红线，也是竞品的死穴）
- ❌ 检测维度堆到 20+ 却没一键修复（只会把审稿变成负担）
